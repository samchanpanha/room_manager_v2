# ផ្នែក ៩ — ក្រមណែនាំសុវត្ថិភាព

សម្រាប់អ្នកគ្រប់គរង IT និងអ្នកគ្រប់ដែលទទួលខុសត្រូវ សម្រាប់ការរក្សាប្រព័ន្ធ
ឱ្យមានសុវត្ថិភាព។ វាប្រើពីការស្គាល់អត្តសញ្ញាណ សិទ្ធិ sessions secrets
ការចូលទិន្ននយ audit និងការប្រតិបត្តិការដែលមានសុវត្ថិភាព។ កំណត់សុវត្ថិភាព
របស់ប្រព័ន្ធក្នុងវា ស្ថិតនៅ [`docs/SECURITY.md`](../SECURITY.md)។

## 9.1 សុវត្ថិភាពការស្គាល់អត្តសញ្ញាណ

| ការបញ្ឆៀង | របៀបដំណើរការ |
|---|---|
| **ការរក្សាពាក្យសមងាត់** | ពាក្យសម្ងាត់ត្រូវបាន hashed ដោយ **scrypt** (មិនដែលរក្សាជាអត្ថបទរាបសព្វ)។ |
| **Sessions** | Sessions ដែល DB គាំទ្រ **អាចកាត់បន្ថយ** បាន។ Cookie ជា **httpOnly** និង **SameSite**។ Sessions ផុតកាល បន្ទាប់ពី `SESSION_TTL_DAYS`។ |
| **ការកំណត់អត្រាការចូល** | ការចូលត្រូវបានកំណត់អត្រា (**10 ដង / នាទី / IP**) ដើម្បីកាត់បន្ថយ brute force។ |
| **ការបង្ខំផ្លាស់ប្ដូរពាក្យសម្ងាត់** | គណនីដែល admin បង្កើត/កំណត់ឡើងវិញ មាន `mustChangePassword` ហើយត្រូវកំណត់ពាក្យសមងាត់ថ្ី នៅពេលចូលដំបូង (sessions ផ្សេង ត្រូវបានកាត់បន្ថយបន្ទាប់មក)។ |
| **2FA (TOTP)** | **ចាំបាច់សម្រាប់ Admin និង Super Admin**។ ការចុះឈ្មោះ QR តាមរយៈ authenticator app។ កូដត្រូវបានពិនិត្យ ជាមួយបង្អួច clock-skew។ admin អាច **reset** 2FA សម្រាប់អនកប្រើដែលត្រូវបានបិទចោល។ Admins **មិនអាចប្រើម៉ូឌូលផ្សេង រហូតដល់ចុះឈ្មោះ**។ |
| **ការចូល portal សមាជិក** | សមាជិកប្រើ**ពាក្យសមងាត់មួយដង (OTP)** ដែលផ្ញើទៅ email/ទូរស័ព្ — កូដត្រូវបាន **hashed ប្រើម្ដង** និង **បិទបន្ទាប់ពី ៥ ដង** (បន្ទាប់មកស្នើមួយថ្មី)។ ការចូល បង្កើត MEMBER user របស់ពួកគេ។ |
| **Kiosk PIN** | Kiosk ការវត្តមាន ប្រើ **scrypt-hashed PIN** សម្រាប់ចុះ/ឡើង ដោយគ្មាន browser session។ |

### អនុសាសន៍
- បើក 2FA សម្រាប់គណនីគ្រប់ដែលមានអំណាច (Admin+ ចាំបាច់។ លើកទឹកចិត្ត សម្រាប់ managers/accountants)។
- ប្រើវដ្ត **ពាក្យសម្ងាត់បណ្ដោះអាសន្ន → បង្ខំផ្លាស់ប្ដូរ** សម្រាប់កម្មករថ្មី។ កុំចែករំលែកពាក្យសមងាត់អចិន្ត្រៃយ៍ ទេ។
- បង្វិលពាក្យសម្ងាត់ បន្ទាប់ពីការបង្កប់គ្នាដែលសង្ស័យ ហើយកាត់បន្ថយ sessions។

## 9.2 សុវត្ថិភាពការអនុញ្ញាត (permissions)

- **RBDC នៅរាល់ endpoint៖** `can(user, action, module, resource?)` ដំណើរការ
  server-side នៅរាល់ API route។ ការលាក់ UI ជាភាពសុទ្ធនិមមិតតែប៉ុណ្ណោះ។
- **ការរឹតជួរ ការពារការចូលឆ្លងអចលនទ្រពយ៖** តួនាទី PROPERTY-scoped
  (Manager/Staff) ឈានដល់តែអចលនទ្រព្ដែលបានចែកចាយរបស់ពួកគេ។ តួនាទី OWN-scoped
  (Owner/Member) ឈានដល់តែកំណត់រឿងផទាល់ខ្លួន។ ការចូលឆ្លងអចលនទ្រពយ/ឆ្លងម្ចាស់
  ត្រឡប់ **403** (បានពិនិត្យដោយតេស្តអវិជ្ជមាន រួមទាំងការព្យាយាម IDOR)។
- **ការបែងចែកអំណាច៖** Staff មិនអាច void វិក្កយបត្រ ផលាស់ប្ដូរតួនាទី ឬបើក
  ledger config បានទេ។ តែ Super Admin void វិក្កយបត្រ។ តែ Accountant+ អនុម័ត
  ការត្រឡប់/របាយការណ៍។ ការផ្លាស់ប្ដូរតួនាទី/សិទ្ធិ ត្រូវការ M01។
- ម៉ាទ្រីសសិទ្ធិ ត្រូវបាន**បិទដោយ CI snapshot/negative tests** ដើម្បី
  ចាប់ការពង្រីកអំណាច ដោយគ្មានកម្មវិធី។

### ការប្រតិបត្តិដែលមានសុវត្ថិភាព
- អនុវត្ត **least privilege**៖ ផ្ដល់តួនាទី/ជួរតូចបំផុត ដែលធ្វើការបាន
  (ឧ. តួនាទី "Cashier" ដែលមានតែ payments write)។
- ចែកចាយ**អចលនទ្រព្យ ដោយមានការពិចារណា** ដល់អ្នកប្រើ PROPERTY-scoped។
- ពិនិត្យតួនាទី ជាប្រចាំ។ **លុប/បិទតួនាទី និងអ្នកប្រើ ដែលមិនប្រើ**។ តួនាទី
  ដែលកំពុងប្រើ មិនអាចលុបបាន — ដកសមាជិកចេញពីវា ជាមុនសិន។
- ចងចាំថា សិទ្ធិប្រសិទ្ធភាព ជា**សរុប (union)** នៃតួនាទីរបស់អ្នកបរើ។

## 9.3 Sessions & ឧបករណ៍
- អ្នកប្រើអាចមើល**sessions & ឧបករណ៍**របស់ពួកគេ (ឧបករណ៍/IP, បង្កើត/ផុតកាល) នៅ
  **My Account / Security** ហើយ**កាត់បន្ថយ** sessionsណាមួយ។
- Admins អាចកាត់បន្ថយ sessions សម្រាប់អ្នកបរើ។ ការផលាស់ប្ដូរពាក្យសម្ងាត់ កាត់បន្ថយ sessions ផ្សេង។
- Sessions ផុតកាលដោយខ្លួនង។ ការងារ**retention** សម្អាត sessions ដែលផុតកាល តាមការកំណត់។

## 9.4 សុវត្ថិភាពទិន្ននយ & ឯកសារ
- **ការរក្សាកសារ៖** ឯកសារទៅ storage ឯកជន (driver S3-compatible ដែលជ្រើស តាមបរិស្ថាន)។ ការទាញយក ប្រើ**signed URLs HMAC ដែល TTL ខ្លី (120s)**។
  អ្នកមិនអាចចូលឯកសារ ដោយប៉ាន់ស្មាន path របស់វា ហើយការចូលឆ្លងអចលនទ្រព្ ត្រូវបានបដិសេធ។
- **Secrets៖** អត្តសញ្ញាណទូទាត់ និង Telegram bot token ត្រូវបាន**ស្គរ ដោយ
  AES-256-GCM** មុនពេលរក្សាទុក ហើយតែងតែបង្ហាញ**masked** តែប៉ុណ្ណោះ។ អថេរបរិស្ថាន
  ជា fallback។ Secrets ស្ថិតនៅ env/secret storage ជានិច្ច មិនមែនក្នុងកូដ ឬ chat ទេ។
- **PII masking៖** ទិន្ននយផ្ទាល់ខ្លួន ត្រូវបាន masked ក្នុង audit logs។
- **ក្ដារស្គរ (Encryption key)៖** secrets ដែលបានស្គរ ត្រូវការ `SETTINGS_ENC_KEY` — ការពារ និង backup
  ក្ដារនេះ ក្រៅបណ្ដាញ។ ដោយគ្មានវា secrets ដែលបានស្គរ មិនអាចបើកបានទេ។

## 9.5 ការធ្វើឱ្យ application រឹងមាំ
- **Security headers / CSP** ត្រូវបានអនុវត្ត។ ការកំណត់អត្រា ក៏គ្របដណ្តប់ webhooks ផង។
- **Webhook integrity៖**
  - Payment webhooks ត្រូវការ **signed secret** (`x-webhook-secret`) ហើយប្រើ
    **ការយោង gateway តែមួយគត់ + idempotency keys** ដើម្បីឱ្យការជូនដំណឹង
    ចម្លង/ធ្វើជំនួស ត្រូវបានបដិសេធ ហើយការទូទាត់ ត្រូវបានបញ្ជាក់**តែម្ដងគត់**។
  - Telegram webhook **ពិនិត្យហត់** — ការធ្វើជំនួស ត្រូវបានបដិសេធ។
- **Member QR / ទំព័រ pay សាធារណៈ៖** `/pay` ត្រូវបាន**កំណត់អត្រា** អនុញ្ញាត**តែ exact-due**
  មិនត្រូវការការចូល និងប្រើ**HMAC-signed** member tokens។

### បញ្ជី penetration (ពីការទទួលយកសុវត្ថិភាព)
ប្រព័ន្ធត្រូវបានសាងសង់ ដើម្បីឆ្លង៖ IDOR ឆ្លងអចលនទ្រព្យ (403) ការឡើងកម្រិតអំណាច
(ការរឹតតួនាទី) ការធ្វើជំនួស webhook (ហត់បដិសេធ) និងការប៉ាន់ស្មាន URL នៅលើឯកសារ
(signed URL តែប៉ុណ្ណោះ)។

## 9.6 Audit & ការទទួលខុសត្រូវ
- **ការផ្លាស់ប្ដូរ foreach ត្រូវបានត្រាត្រួតពិនិត្យ** ជាមួយ actor ពេលវេលា មុន/បន្ទាប់ និង IP។
- Audit log ជា **append-only ជាមួយ hash chain ដែលមើលឃើញការប៉ះប៉ាល់**។ admin អាច
  **ពិនិត្យជួរ** (`/api/audit/verify` ក្រោម Security)។
- **ប្រវតតិ audit មិនដែលសម្អាត** ដោយការងារ retention។
- ប្រើ audit log ដើម្បីស៊ើបអង្កេតវិវាទ កែតម្រូវបរតិបត្ិការ (តាមការរំលំត្រឹមត្រូវ)
  និងបង្ហាញការទទួលខុសត្រូវ។
